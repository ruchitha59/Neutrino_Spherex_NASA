## Processing status values

- `complete`: at least one scientifically gated comparison completed and no manifest input was missing.
- `partial`: useful frames were prepared or some comparisons completed, but inputs or comparisons were incomplete.
- `failed`: no eligible same-release/same-band group or no usable frames could be prepared.

A comparison has its own status, including `complete`, `blocked_incompatible` or `blocked_alignment`.

## Actual processing JSON structure

The Job009 `processing.json` contains:

- Job metadata: `schema_version`, `job_id`, `created_utc`, `software_version`
- Input information: `input_manifest`, `input_observation_count`, `usable_local_observation_count`, `missing_or_failed_input_count`, `input_failures`
- Selection information: `groups_found`, `selected_group`
- Processing outputs: `frames`, `comparisons`
- Quality and configuration information: `reference_grid`, `reprojection`, `masking`, `calibration_and_normalization`, `alignment_tolerances`
- Final reporting: `warnings`, `errors`, `status`, `candidate_count`

## Member 3 result response mapping

Member 3 can map Member 2 outputs to the PRD response as follows:

- `frames[].preview` â†’ `frames[].preview_url` after creating a safe server-generated media URL.
- `frames[].timestamp` â†’ `frames[].obs_time`.
- `frames[].collection` â†’ `frames[].collection`.
- `frames[].mask_counts` â†’ `frames[].quality_summary`.
- `comparisons[].difference_preview` â†’ `difference_url` when a completed comparison exists.
- `comparisons[].significance_preview` â†’ an optional significance preview URL.
- `candidates.json` candidate records â†’ `candidates`.

These are integration mappings, not fields already generated by Member 2.

Never return the local `source_file`, `aligned_fits` or absolute filesystem paths to a public browser. Member 3 must resolve safe, server-generated media URLs and enforce path allowlists.
